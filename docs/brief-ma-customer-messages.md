## ليش

**القصة:** رقم البوت مش على أي تلفون، فالوحيد اللي بيقرأ رسائله هو البوت. أحمد طلب، وبعد نص ساعة كتب «وين طلبي؟» على نفس الرقم. اليوم:
- الجلسة صارت `order_placed`، فالرسالة بتفتح جلسة جديدة، **وبيوصله المنيو كله** (`CLAUDE.md`، Known gaps).
- والرسالة **ما بتبين بصفحة طلبه** باللوحة: قاعدة 5 بـ`messages()` («what comes after the customer's last order is no order's yet»).
- يعني أحمد سأل، وما حدا بالمطعم عرف.

**قرار محمد (13 أكتوبر):** الحل بجزئين. **هاد الجزء الأول، والمحرّك أول:** بعده الزبون ما عاد يوصله المنيو، بيوصله حالة طلبه ورقم المطعم. والموظف بيشوف الرسالة بمحادثة الطلب. الشاشة (علامة، صوت، صوتيات) ببريف م-ب.

### النصوص — حرفيا، ولا حرف زيادة

**أ. سطر الحالة (أول السطر، لكل طلب ماشي، من الأقدم للأحدث):**

| الحالة | النص |
|---|---|
| `pending_acceptance` | `استلمنا طلبك رقم [رقم الطلب]، وما أكّدناه بعد.` (جديد) |
| `accepted` | نفس رسالة التأكيد الجديدة (ب) |
| `preparing` | `نحضّر طلبك رقم [رقم الطلب] الآن.` (جديد) |
| `ready` استلام / توصيل | نفس رسالة الجاهز الجديدة (ب) |

**وبعده (جديد):**
- `وصلت رسالتك للمطعم.`
- `للتواصل مباشرة: [رقم المطعم]` (بس إذا `contact_phone` مش NULL. NULL = ولا سطر، نفس قاعدة `HANDOFF_AR`)
- `لطلب جديد، اكتب «منيو».`

**لطلب خالص بس** (ما في طلب ماشي)، أول سطر بدل سطر الحالة و«وصلت»:
- `وصلت رسالتك للمطعم بخصوص طلبك رقم [رقم الطلب].` (جديد). ليش بلا حالة: لو كتبله «سلّمنا طلبك» وهو بيشتكي إنه ناقص، رح يبين إنه المطعم بيدافع عن حاله.

**الشكل الكامل، حرفيا (`\n` بين السطور، بلا سطر فاضي):**

```
استلمنا طلبك رقم 108، وما أكّدناه بعد.
وصلت رسالتك للمطعم.
للتواصل مباشرة: 0790000099
لطلب جديد، اكتب «منيو».
```

```
طلبك رقم 107 جاهز للاستلام.
نحضّر طلبك رقم 108 الآن.
وصلت رسالتك للمطعم.
للتواصل مباشرة: 0790000099
لطلب جديد، اكتب «منيو».
```

```
وصلت رسالتك للمطعم بخصوص طلبك رقم 108.
للتواصل مباشرة: 0790000099
لطلب جديد، اكتب «منيو».
```

**ب. رسائل الحالة الموجودة (`ORDER_STATUS_MESSAGE_AR`) بالرقم:**

| المفتاح | اليوم | بعد |
|---|---|---|
| `accepted` | `أكّدنا طلبك.` | `أكّدنا طلبك رقم [رقم الطلب].` |
| `ready.pickup` | `طلبك جاهز للاستلام.` | `طلبك رقم [رقم الطلب] جاهز للاستلام.` |
| `ready.delivery` | `طلبك خرج للتوصيل.` | `طلبك رقم [رقم الطلب] خرج للتوصيل.` |

### قرارات البريف (من Claude، بتمشي إلا إذا الريبو بيقول غير)

- **ثلاث متغيّرات بيئة** بـ`env.ts` تبع المحرّك، بنفس شكل `REORDER_MIN_AGE_MINUTES`:
  - `RELAY_OPEN_ORDER_MAX_MINUTES`، الافتراضي `180`.
  - `RELAY_CLOSED_ORDER_MINUTES`، الافتراضي `60`.
  - `RELAY_REPLY_QUIET_MINUTES`، الافتراضي `10`.
  - `setup-env.ts` بيثبّتهم على الافتراضي، و`.env.example` بيذكرهم. ليش متغيّرات: التجربة على اللاب بدها دقايق مش ساعات.
- **كل الأوقات بساعة القاعدة** (`now()` و`make_interval`)، مش ساعة Node، زي مهلة الجلسة و«آخر طلب لك».
- **وقت خلوص الطلب** = `COALESCE(max(order_status_history.changed_at), orders.created_at)`، نفس `status_changed_at` بـ`orders.service.ts`.
- **الربط:** المحرّك بيقرّر الطلب، والـwebhook (اللي بيملك صف الرسالة الواردة) بيكتب `order_id` على صفّه بنفس المعاملة. هيك المحرّك ما بيحتاج معرّف الصف.
- **السكوت 10 دقايق محفوظ على الزبون:** `customers.relay_replied_at`، بيتقرا ويتكتب **تحت قفل `FOR UPDATE` على صف الزبون**، فرسالتين بنفس اللحظة ما بيطلّعوا سطرين.
- **السطر بينبعت جوّا معاملة الرسالة**، زي باقي ردود المحادثة (مش بعد الـCOMMIT)، **و`orderId` = الطلب المربوط**، فالـsaving sender بيحفظه بـ`outbound_messages.order_id` وبيطلع بمحادثة الطلب (قاعدة 1). فشل الإرسال بيسحب المعاملة كلها، وميتا بتعيد.
- **التفاعل بأول `handleInbound`**، قبل قراءة المطعم وقبل أي جلسة.

## 2. م-1 · الهجرة 0016

```sql
-- 0016: brief م-أ — a customer's message after an order reaches the
-- restaurant.
--
-- inbound_messages.order_id: the order the engine relayed this message to.
-- NULL = not relayed (an ordering message, one before any order, a
-- reaction). Tied to the restaurant by the tenant key, as outbound_messages
-- (0013). ON DELETE SET NULL (order_id) — the column list keeps
-- restaurant_id: the customer's own words are the one thing we hold no copy
-- of, and an order going never takes them with it.
--
-- customers.relay_replied_at: the last time the relay line went to this
-- customer; the next waits RELAY_REPLY_QUIET_MINUTES. Read and written under
-- FOR UPDATE on the customer's row.
BEGIN;

ALTER TABLE inbound_messages
  ADD COLUMN order_id uuid NULL;

ALTER TABLE inbound_messages
  ADD CONSTRAINT inbound_messages_order_fk
  FOREIGN KEY (order_id, restaurant_id)
  REFERENCES orders (id, restaurant_id) ON DELETE SET NULL (order_id);

CREATE INDEX idx_inbound_messages_order
  ON inbound_messages (order_id, received_at)
  WHERE order_id IS NOT NULL;

ALTER TABLE customers
  ADD COLUMN relay_replied_at timestamptz NULL;

COMMIT;
```

**ولا شي غيره.** الـRLS والصلاحيات القائمة على الجدولين بتغطّي العمودين.

- **`schema.ts`:** `inboundMessages.orderId` (`uuid("order_id")`) و`customers.relayRepliedAt` (`timestamp("relay_replied_at", { withTimezone: true })`). الـFK المركّب ما بينعكس، زي `outbound_messages`.

## 4. م-3 · المحرّك

**أ. السياق:** `ConversationContext` بياخد حقلين **إجباريين** (بنفس سبب `body` و`deferred`: حقل اختياري بينتسى بصمت):
- `messageType: string`: من `message.type`.
- `relayed: { orderId: string | null }`: خانة ناتج، المستدعي بيعطيها `{ orderId: null }`، و`handleInbound` بيعبّيها لما يربط. (نفس فكرة `deferred`: المستدعي اللي بيملك المعاملة بيكمّل الشغل.)

**ب. الـwebhook:** الـ`insert` بيرجّع `id`. بعد `handleInbound`، إذا `relayed.orderId` مش NULL: `UPDATE inbound_messages SET order_id = … WHERE id = …` **بنفس المعاملة**.

**ج. التفاعل:** أول سطر بـ`handleInbound`: `messageType === "reaction"` ← نتيجة جديدة `"reaction_ignored"`، وولا شي تاني (ولا قراءة، ولا إرسال، ولا `last_message_at`).

**د. القاعدة** (ملف لحاله، مثلا `src/conversation/customer-relay.ts`، بشكل الريبو: قرار صافي + غلاف I/O رفيع)، **بعد التوجيه للجلسة الشغّالة وقبل بوابة الدوام** (م-0 #3):
1. **«منيو»** (`matchCommand(body ?? "") === "menu"`) ← ما في قاعدة، كمّل للمسار القائم.
2. **الاستعلام** (جوّا معاملة الرسالة، تحت RLS المطعم، الزبون بالرقم): طلباته الماشية اللي `created_at > now() - make_interval(mins => RELAY_OPEN_ORDER_MAX_MINUTES)`، وطلباته الخالصة (`completed` · `cancelled`) اللي وقت خلوصها `> now() - make_interval(mins => RELAY_CLOSED_ORDER_MINUTES)`. `expired` ما بيدخل.
3. **ولا طلب** ← كمّل للمسار القائم.
4. **في طلب:**
   - الطلب المربوط = آخر طلب ماشي، وإلا آخر طلب خالص.
   - `SELECT … FROM customers … FOR UPDATE` على صف الزبون، و`relay_replied_at`.

   - `ctx.relayed.orderId` = المربوط.
   - نتيجة جديدة `"relayed"`. **ولا جلسة بتنفتح، ولا زبون جديد بينكتب** (الزبون موجود أصلا).
5. **سطر `info`:** المطعم · الرقم مقنّع · الطلب المربوط · السطر انبعت أو سكوت.

**هـ. المُراقِب:** `ClaimedOrder` واستعلام الالتقاط بياخدوا `order_number`، والرسالة بالرقم. **ولا شي تاني بالمُراقِب.**

- **«آخر طلب خالص» = آخر طلب *خلص*** (وقت الخلوص، وبعده `created_at`)، مش آخر طلب *انعمل*. ليش: زبون بيكتب «الطلب ناقص» غالبا قصده اللي استلمه هلق. ما بيفرق إلا لما طلبين يخلصوا خلال ساعة.
- الطلب الخالص ما بينقرأ إلا لما ما في طلب ماشي (القرار 2 بيخلّيه بلا معنى غير هيك).
- الحدود: الطلب الماشي `created_at > now() - 180 دقيقة` حرفيا من البريف (طلب عمره 180:00 بالزبط ما بينحسب). دقايق السكوت: **عند 10:00 بالزبط السطر بيروح** (`>=`، زي مهلة الجلسة)، ومنفحوص على الدالة الصافية مش على القاعدة (نفس سبب اختبار 3 بح).
- `ConversationService` أخدت باراميتر خامس `relayMinutes` (كائن بالتلاتة)، افتراضه من `env.ts`.
- `.env.example`: الأسطر التلاتة **وفوقهم سطر تعليق واحد** — زي كل متغيّر تاني بالملف. البريف قال «الأسطر التلاتة بس».
- الـwebhook: خطوة ٥ جديدة (كتابة `order_id`)، والإرسال بعد الـCOMMIT صار ٦ بالتعليقات.
- الاختبارات: `customer-relay.test.ts` فيه 1–22 حرفيا، وخمسة زيادة: ساعة القاعدة (شهر قدّام وورا، للطلب الماشي ولدقايق السكوت) · الدقايق هي دقايق الخدمة (4 / 2 / 1 زي تجربة اللاب) · `expired` مش ماشي ولا خالص · حد السكوت على الدالة الصافية · `decideRelay`. **23 هو `notifier.test.ts`** 1 و3 و5 (وكل اختبار فيه نص) — صارت بالرقم بـم-2.
- **الاختبارات القائمة اللي تغيّرت (السبعة):** رسالتها صارت «منيو» بدل «مرحبا»، والمتوقّع ما تغيّر. اتأكّدت إنها كلها بتوقع بـ«مرحبا» مع القاعدة (7 من 7)، وبتمرق بـ«منيو». وتعليق `amountLines` بـ`order.test.ts` اتصلّح.
